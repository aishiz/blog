## Что строим: архитектура агента

Один файл `agent.py`, наращиваемый по ходу статьи. Ключевые единицы:

1. **Клиент LLM** — `openai.OpenAI(base_url=..., api_key=...)`. Провайдер-агностик: код одинаков для Cloud.ru Foundation Models, локального vLLM/Ollama, OpenRouter — меняется только `base_url` и имя модели.
2. **Реестр тулов** — словарь `{имя: (json_schema, python_функция)}`. JSON-схемы уходят в `tools=` запроса; по имени из ответа модели вызываем соответствующую функцию.
3. **Агент-луп** — `while` до тех пор, пока модель возвращает `tool_calls`: отправляем сообщения → если модель просит тулы, исполняем каждый, добавляем результаты как `role: "tool"` сообщения → повторяем; когда модель вернула обычный текст без `tool_calls` — это финальный ответ, выходим.
4. **Песочница** — все файловые/шелл-операции ограничены одной рабочей папкой (`WORKDIR`), пути нормализуются и проверяются на выход за пределы; `run_shell` с таймаутом.

## Тулы (4 штуки)

| Тул | Что делает | Границы безопасности |
|---|---|---|
| `read_file(path)` | вернуть содержимое файла | путь только внутри `WORKDIR` |
| `write_file(path, content)` | записать/перезаписать файл | путь только внутри `WORKDIR` |
| `list_dir(path)` | список файлов/папок | путь только внутри `WORKDIR` |
| `run_shell(cmd)` | выполнить команду, вернуть stdout/stderr/код | `cwd=WORKDIR`, таймаут (напр. 30 c) |

Безопасность проговариваем явно и заметно: агент выполняет произвольный код/команды от модели — запускать только в изолированной папке/контейнере, не на рабочем проекте.

## Бэкенд и интеграция Cloud.ru Foundation Models

Дефолтный «featured» endpoint — **Cloud.ru Evolution Foundation Models** (OpenAI-совместимый API, function calling поддерживается):

```python
client = OpenAI(
    base_url="https://foundation-models.api.cloud.ru/v1",  # без завершающего слэша — как в доке
    api_key=os.environ["CLOUDRU_API_KEY"],  # Key Secret сервисного аккаунта
)
```

Показываем: где взять ключ (Консоль → Пользователи → Сервисные аккаунты → Учетные данные доступа, скоуп Foundation Models), выбор модели с function calling, первый запрос. **ID моделей требуют префикс провайдера** — `ai-sage/GigaChat3-10B-A1.8B` (пример из квикстарта, дефолт туториала), `ai-sage/GigaChat3.5-432B-A28B`, `moonshotai/Kimi-K2.6`, `zai-org/GLM-5.1`, `deepseek-ai/DeepSeek-V4-Pro`.

Рядом — короткая врезка «тот же код, другой провайдер»: локальный vLLM (`http://localhost:8000/v1`), Ollama (`http://localhost:11434/v1`), OpenRouter. Смысл: читатель понимает, что научился универсальному стандарту, а не привязке к вендору.

## Арка статьи (5 шагов)

**Вступление** — крючок: «агент» демистифицируется до `while` вокруг tool-calling; что соберём; дисклеймер про песочницу.

**Шаг 1. Голый вызов LLM.** Подключаем Cloud.ru FM, делаем первый chat-запрос. Показываем: модель умеет только генерить текст, «сделать» ничего не может. Ставим вопрос — как дать ей руки.

**Шаг 2. Первый тул `read_file` и анатомия tool-calling.** Описываем один тул JSON-схемой, передаём в `tools=`. Разбираем протокол по шагам: ответ модели с `tool_calls` (id, имя, аргументы) → мы исполняем функцию → возвращаем результат сообщением `role: "tool"` с тем же `tool_call_id` → модель формулирует ответ. Это ядро — здесь главный интерактив-визуализатор.

**Шаг 3. Полный агент-луп + остальные тулы.** Оборачиваем в `while`, добавляем `list_dir`, `write_file`, `run_shell` (все в песочнице). Теперь агент делает многошаговые задачи сам.

**Шаг 4. Реальная задача.** Кладём в песочницу мини-проект с багом и тестом; просим агента «почини так, чтобы тесты прошли». Показываем реальный трейс: агент листает → читает → правит → запускает тесты → видит фейл → правит снова → зелёно. Это кульминация.

**Шаг 5. Прод-нюансы.** Лимит итераций (защита от бесконечного цикла), обработка ошибок тула (вернуть ошибку модели, а не падать), параллельные `tool_calls` в одном ответе, безопасность `run_shell`, и куда расти (стриминг, суб-агенты, вложенные тулы — со ссылками на существующие статьи блога agent-harness / ai-agents-landscape / mcp-protocol-deep-dive).

**TL;DR** — сжатый чек-лист «что такое агент за 5 пунктов».

## Интерактив (фишка блога)

1. **AgentLoopVisualizer** (главный, обязательный). Реальный трейс мини-агента по задаче из Шага 4: последовательность шагов user → LLM → tool_calls → exec → tool result → … → финальный ответ. Пользователь листает шаги вперёд/назад и видит: (а) что на этом шаге сделала модель, (б) какой тул вызван с какими аргументами, (в) как растёт список сообщений (контекст). Цель — сделать невидимый цикл осязаемым.
2. **ToolCallAnatomy** (опционально, если не раздувает). Мини-схема одного round-trip: `assistant.tool_calls[{id, name, args}]` → наша функция → `{role:"tool", tool_call_id, content}`. Статичная/лёгкая интерактивность.

Компоненты следуют конвенциям блога: `.tsx` в `src/components/article/`, inline `css`-объект `React.CSSProperties`, CSS-переменные темы, дефолтный экспорт без пропсов, без новых npm-зависимостей, детерминированные данные (без `Math.random`/`new Date`). Трейс в визуализаторе — реальный прогон, зашитый как данные.
