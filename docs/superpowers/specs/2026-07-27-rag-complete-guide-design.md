## Аудитория и голос

Как и у остальных статей блога: практикующие AI/ML-инженеры, без воды, с кодом и конкретными цифрами, лёгкая ирония в духе «шизы» сайта. При таком объёме — особое внимание к разбивке текста (Callout/StepList/QuantCard/таблицы), чтобы длинный текст не превратился в сплошную стену.

## Контентная структура

1. **Вступление** — какую проблему решает RAG (устаревшие знания модели, галлюцинации, приватные/проприетарные данные), почему это не «просто прикрутить векторную БД».
2. **Механики** (раздел на каждую, с кодом):
   - Чанкинг: fixed-size, recursive, semantic — компромиссы размера чанка и overlap.
   - Эмбеддинги: что это, обзор открытых моделей (BGE, E5, GTE, мультиязычные варианты), размерность.
   - Векторный поиск и индексация: cosine similarity, приближённый поиск (HNSW), обзор ландшафта векторных БД.
   - Hybrid search: BM25 + vector, почему чистый vector search промахивается на точных/ключевых запросах, Reciprocal Rank Fusion.
   - Reranking: cross-encoder vs bi-encoder, зачем нужен второй проход.
   - Query transformation: query rewriting, HyDE, multi-query, декомпозиция сложных запросов.
3. **Оценка RAG**: метрики (faithfulness, context precision/recall, answer relevancy), фреймворк RAGAS — как понять, что система вообще работает, а не просто выглядит рабочей.
4. **Архитектуры** (обзорно-сравнительно, не отдельный deep-dive на каждую): naive RAG → advanced RAG → modular RAG → agentic RAG → Self-RAG / Corrective RAG (CRAG) → GraphRAG. Сравнительная таблица «что решает / когда применять / сложность».
5. **Полный рабочий код** — два сквозных примера одной и той же логики (чанкинг → эмбеддинги → индекс → hybrid retrieval → rerank → генерация):
   - «С нуля», лёгкий стек без API-ключей: `sentence-transformers` (эмбеддинги), `ChromaDB` (векторное хранилище), `rank_bm25` (BM25), cross-encoder модель (reranking). Читатель может запустить локально.
   - То же самое через продакшн-стек: LangChain или LlamaIndex как оркестратор, Qdrant/Weaviate как хранилище — чтобы показать, что именно абстрагируют фреймворки относительно «сырой» версии.
6. **Опенсорс-экосистема** — курированные таблицы по категориям: оркестраторы (LangChain, LlamaIndex, Haystack), векторные БД (Chroma, Qdrant, Weaviate, Milvus, pgvector, FAISS), модели эмбеддингов (BGE, E5 и варианты), реранкеры (bge-reranker, cross-encoder/ms-marco), инструменты оценки (RAGAS, TruLens).
7. **TL;DR**.

## Интерактивные компоненты

Четыре компонента, каждый закрывает механику(и), которые иначе остались бы только текстом и кодом.

### 1. `RagPipelinePlayground.tsx`

Флагманский компонент. Игрушечный корпус документов (небольшой, тематически про AI/ML, чтобы совпадало с голосом блога). Пользователь вводит запрос → компонент показывает: результаты чистого vector search (по косинусной близости к toy-эмбеддингам корпуса) vs BM25 vs результат hybrid-фьюжна (RRF) → как reranking переставляет порядок топ-результатов → финальный собранный контекст, который пошёл бы в промпт генерации. Закрывает векторный поиск, hybrid search, reranking одним живым потоком.

Данные (toy corpus + toy embeddings/BM25-подсчёты) — детерминированные, посчитанные заранее (аналогично `BpeTrainerViz`: реальный алгоритм на фиксированном небольшом наборе данных, не имитация чисел).

### 2. `RagArchitectureExplorer.tsx`

Кликабельная схема: переключаешь архитектуру (naive / advanced / modular / agentic / self-RAG / GraphRAG) и видишь, как меняется путь запроса через систему (какие узлы/шаги активны, куда идут стрелки). Аналог по духу `MoeExplorer`/`AgentLoopViz` — переключение состояния, не текст.

### 3. `ChunkingVisualizer.tsx`

Реальный кусок демонстрационного текста. Переключатель стратегии (fixed-size / recursive / semantic) — компонент показывает, где именно проходят границы чанков при каждой стратегии, подсвечивая чанки чередующимися цветами (аналог токен-чанков в `TokenizerPlayground`). Возможно, ползунок размера чанка/overlap для fixed-size, чтобы почувствовать компромисс на пальцах.

### 4. `EmbeddingSpaceExplorer.tsx`

2D-визуализация эмбеддингов на ~15–20 примерах предложений. **Данные — настоящие**: эмбеддинги считаются один раз оффлайн (Python-скрипт, `sentence-transformers`, открытая модель), координаты сводятся к 2D (PCA или аналог) и сохраняются как статичные данные прямо в компоненте — в браузер модель не грузится (веса весят сотни МБ, непрактично для клиента). Клик на предложение показывает ближайших соседей по смыслу и оценку косинусной схожести, посчитанную из тех же настоящих эмбеддингов.

Все компоненты — новые файлы в `src/components/article/`, следуют существующим конвенциям каталога (инлайн-стили через CSS-переменные темы, `role="button"`+`tabIndex`+`onKeyDown` для кликабельных не-нативных элементов, `aria-label` на текстовых/интерактивных полях), `client:visible`.

## Технические детали реализации

- Для `EmbeddingSpaceExplorer` потребуется одноразовый оффлайн-расчёт эмбеддингов: установить `sentence-transformers` в Python (временно, не добавляется как зависимость проекта — это Node/Astro проект), прогнать скрипт, получить числа, вставить как статичные данные в TSX. Сам пакет `sentence-transformers` в `package.json` не попадает.
- Никаких новых npm-зависимостей для остальных трёх компонентов не требуется — это чистая клиентская логика на toy-данных, как `BpeTrainerViz`.
- Все числа в прозе (similarity-оценки, примеры retrieval-результатов) должны быть проверены реальным расчётом перед тем, как попасть в текст — как это было сделано для статьи про токенизацию, не оценки на глаз.

## Вне скоупа

- Реальные вызовы LLM (генерация ответа) — код примеров показывает, куда подставить вызов модели, но не делает реальный API-запрос как часть демо-компонентов (это слишком дорого и требует ключей от читателя блога).
- Развёртывание векторных БД в проде (Kubernetes, шардирование и т.п.) — за рамками статьи, это отдельная большая тема.
- Полный deep-dive на каждую архитектуру (это по объёму каждая — отдельная статья); здесь — обзорно-сравнительно.

- Все четыре интерактивных компонента визуально проверены в превью (`npm run preview`) — плейграунд реально считает retrieval/rerank на toy-корпусе, chunking-визуализатор корректно режет текст под каждую стратегию, embedding-эксплорер показывает настоящие посчитанные соседства.
- Статья прогнана через `/unslop` перед коммитом.
- Обложка подключена, статья закоммичена и запушена.
