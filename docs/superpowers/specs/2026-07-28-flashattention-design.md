# Статья: FlashAttention — как реально считается attention на GPU

Дата: 2026-07-28

## Цель

Новая статья в блоге (категория «фундамент») про FlashAttention: IO-aware алгоритм attention, который не материализует полную N×N-матрицу внимания в HBM, а считает её блоками через SRAM с online softmax. Продолжение линии уже опубликованных статей про KV-кэш и спекулятивный декодинг — оба текста подводят читателя к тезису «decode упирается в память, а не в FLOPs»; эта статья закрывает третий угол той же истории — сам forward pass attention.

Слаг: `flashattention`. Файл: `src/content/blog/flashattention.mdx`.

## Аудитория и голос

Та же аудитория и голос, что у остальных статей блога: практикующие AI/ML-инженеры, без воды, с кодом и конкретными цифрами, лёгкая ирония в духе «шизы» сайта.

## Глубина

Концептуально + немного формул. Идея тайлинга и online softmax объясняются на пальцах с диаграммами и интерактивом, rescaling-формулы даю, но без полного математического вывода и без разбора backward pass в деталях (backward — только концептуально, идея recomputation).

## Ограничение среды: нет рабочего GPU

На машине, где пишется статья, физически есть NVIDIA RTX 2070 Super, но `nvidia-smi`/CUDA сейчас недоступны (mismatch версии загруженного kernel-модуля и userspace NVML-библиотеки — драйвер обновили, модуль не перезагрузили). Чинить это (reboot/modprobe-цикл) в рамках этой сессии не будем — решили планировать статью без GPU:

- Все цифры по памяти/скорости naive vs FlashAttention — **цитируются из официального источника** (репозиторий Dao-AILab/flash-attention, статьи FlashAttention / FlashAttention-2 Tri Dao et al.) с явной атрибуцией и ссылкой в тексте. Никаких «я замерил» там, где не мерено.
- Код в статье реальный и синтаксически корректный (проверяемый по официальной документации PyTorch/flash-attn), но:
  - наивная реализация attention — на PyTorch, **без CUDA**, численно проверяется на CPU (маленькие тензоры) на эквивалентность с тайлинг/online-softmax версией — это реально прогоняется и подтверждается перед публикацией;
  - вызов `torch.nn.functional.scaled_dot_product_attention` / `flash_attn` — синтаксис даю по документации, в тексте честно помечаю, что локально не гонялось (нет рабочего CUDA на этой машине).

## Контентная структура (черновой план разделов)

1. **Зачем** — почему naive attention упирается в HBM bandwidth, а не в FLOPs. Явные кросс-ссылки на уже опубликованные статьи про [KV-кэш](/blog/kv-cache/) и [спекулятивный декодинг](/blog/speculative-decoding/) — тот же тезис «memory-bound, не compute-bound», третья грань той же истории.
2. **GPU memory hierarchy** — SRAM (маленькая, ~десятки МБ, очень быстрая) vs HBM (десятки ГБ, на порядок медленнее) → интерактив «Memory Hierarchy».
3. **Naive attention** — почему он трижды гоняет N×N-матрицу через HBM (записать QKᵀ → прочитать для softmax → записать → прочитать для ×V), реальный подсчёт объёма трафика в O(N²) для памяти при том что FLOPs те же, что и у tiled-версии.
4. **Тайлинг** — грузим блоки Q/K/V в SRAM целиком, считаем частичный результат, не материализуя полную матрицу → интерактив «Tiling Simulator» (флагманский).
5. **Online softmax** — концептуально + rescaling-формулы (обновление текущего max и sum при появлении нового блока, corrective factor для уже накопленного результата), без полного вывода.
6. **Backward pass** — коротко: recomputation вместо хранения полной матрицы внимания (trade compute for memory).
7. **v1 → v2 → v3, коротко** — что менялось: лучшая параллелизация по seq/batch, меньше non-matmul FLOPs, warp-specialization в v3. Пара абзацев, не отдельные подробные разделы на каждую версию.
8. **Benchmark: naive vs Flash** → интерактив «Benchmark Compare»: память и время на разных длинах контекста, цифры из официального источника со ссылкой.
9. **Код** — наивный attention руками (PyTorch, CPU, с проверкой численной эквивалентности тайлинг-версии) + пример вызова `scaled_dot_product_attention`/`flash_attn` (синтаксис по докам, пометка «не гонялось локально — нет CUDA»).
10. **Где встретишь на практике** — все инференс-движки используют FlashAttention под капотом; ссылка на уже опубликованный [гайд по инференс-движкам](/blog/llm_inference_engines_complete_guide/), уточнение отличия от PagedAttention (тот про управление памятью KV-кэша, этот — про сам алгоритм вычисления attention).
11. **TL;DR**.

## Интерактивные компоненты

Три компонента, каждый проще по объёму работы, чем флагманы прошлых статей (RAG-статья задавала верхнюю планку сложности — здесь так не нужно).

### 1. `MemoryHierarchyExplorer.tsx`

- Визуализация SRAM vs HBM: размер и bandwidth (реальные порядки величин для GPU уровня A100/H100, с источником в тексте рядом).
- Простая статичная/полу-интерактивная диаграмма (два «бака» разного размера, подписанные скоростью чтения/записи), возможно slider или переключатель «на сколько порядков SRAM быстрее».
- `client:visible`.

### 2. `TilingSimulator.tsx` (флагманский)

- N×N-сетка (маленькая, например 8×8 условных блоков), кликабельная/пошаговая — как в `RagArchitectureExplorer` пошаговый плеер (кнопка «следующий блок» + автоплей).
- На каждом шаге: подсвечивается текущий блок Q/K/V, который «загружен» в SRAM; показывается обновление текущего running max и running sum (online softmax) числами рядом; блоки, уже обработанные — тускнеют/помечаются как готовые.
- Явно видно: полная N×N-матрица никогда не существует в памяти целиком — в любой момент видно только один блок.
- `client:visible`, паттерн клавиатурной доступности (`role="button"`, `tabIndex`, `onKeyDown`) как в остальных пошаговых компонентах сайта.

### 3. `BenchmarkCompare.tsx`

- Переключатель длины контекста (пресеты: например 1K/4K/16K/64K токенов).
- Для каждой длины — сравнение naive vs FlashAttention по объёму памяти (МБ, читаемой/записываемой) и по времени — цифры берутся из официального бенчмарка (Dao-AILab/flash-attention repo или статьи), захардкожены в компоненте как константы с комментарием-источником в коде.
- Простая столбчатая визуализация (аналогичная по духу существующим `QuantCard`/статичным сравнениям, но интерактивная через переключатель длины).
- `client:visible`.

Все три — новые файлы в `src/components/article/`, следуют существующим конвенциям каталога: инлайн-стили через CSS-переменные темы (`var(--accent)`, `var(--bg-card)` и т.д.), без новых npm-зависимостей (тайлинг и memory-hierarchy — чистая вёрстка/state, benchmark — статичные числа с источником).
