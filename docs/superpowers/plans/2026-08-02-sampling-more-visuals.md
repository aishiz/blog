## Global Constraints

**Проверенная математика (сверено по исходникам vLLM и HF; отклонение — дефект):**
- Порядок vLLM: `temperature → min_p → top_k → top_p → один финальный softmax`.
- Порядок HuggingFace: `temperature → top_k → top_p → min_p`.
- temperature делит логиты до softmax.
- top-k маскирует строго меньшее, чем k-е по величине значение.
- top-p оставляет минимальный набор с кумулятивной массой ≥ p (граничный токен включается), считая её по **перенормированному** распределению текущих выживших; лидер сохраняется всегда.
- min-p: порог `min_p × max(вероятностей)`, маскируется строго меньшее.
- **Важная тонкость, подтверждённая чтением `MinPLogitsWarper` в HF:** решение min_p **инвариантно** к предшествующей перенормировке — и порог, и вероятности масштабируются одним множителем, сравнение сокращается. Поэтому «в HF лидер потолстел и порог стал строже» — **неверная** формулировка, писать её нельзя.
- **Настоящий механизм расхождения порядков:** min_p, отработав первым (vLLM), убирает хвостовые токены; top_p затем суммирует перенормированные, то есть раздутые, вероятности и добирает порог **раньше**, оставляя меньше токенов. В HF top_p считает по ещё не прорежённому распределению.
- **Проверенный расходящийся пример** (получен численно, использовать его):
  распределение `a=0.40, b=0.30, c=0.20, d=0.06, e=0.04`; параметры `min_p=0.15, top_k=0 (off), top_p=0.92`.
  vLLM → выживают `a, b, c` (3 токена). HF → выживают `a, b, c, d` (4 токена).

## Task 1: TemperatureShape (Часть 1)

**Files:** Create `src/components/article/TemperatureShape.tsx`

**Что должен показывать.** Самую базовую вещь статьи: температура действует на **логиты**, до softmax, и меняет остроту распределения. Сейчас Часть 1 вообще без визуала, а первый интерактив читатель встречает уже в Части 2 сразу с четырьмя ручками.

Требования к поведению:
- Две панели бок о бок для одного набора токенов: слева **логиты** (в том числе отрицательные — шкала должна это корректно показывать), справа **вероятности после softmax**.
- Один ползунок — температура, диапазон примерно 0.1…2.0.
- При движении ползунка видно: логиты делятся на T (левая панель меняет масштаб), распределение справа заостряется при низкой T и выравнивается при высокой.
- Числовая подпись, делающая мысль явной: например, отношение вероятности лидера ко второму месту — при T→0 оно улетает, при высокой T стремится к 1. Это и есть «острота».
- Токены и логиты — свои, не копировать распределение из `SamplingPlayground` (чтобы читатель не путал два разных примера). Пометить как иллюстративные.
- Никаких top-k/top-p/min-p здесь: компонент про одну ручку.

**Проверка.** Написать одноразовый скрипт в скретчпаде, портирующий softmax компонента, и убедиться: сумма вероятностей ≈ 1 на всём диапазоне T; при уменьшении T отношение лидера ко второму монотонно растёт; при T=2 распределение заметно ровнее, чем при T=0.2. Приложить реальный вывод.

**Сборка и коммит:** `npm run build` (ожидаемо 35 страниц, без ошибок), затем коммит только этого файла.

## Task 2: EngineOrderDuel (Часть 3)

**Files:** Create `src/components/article/EngineOrderDuel.tsx`

**Что должен показывать.** Главное заявление статьи — что порядок ручек в vLLM и HF разный и это меняет результат — сейчас только текстом в Callout. Компонент обязан это **доказать**: одни и те же параметры, два конвейера, разные наборы выживших.

Требования к поведению:
- Две колонки: слева `vLLM: temperature → min_p → top_k → top_p`, справа `HuggingFace: temperature → top_k → top_p → min_p`. Порядок подписан в каждой колонке.
- Общие для обеих колонок ползунки: `min_p`, `top_p` (и `top_k`, если помещается — можно оставить фиксированным «off», тогда подписать это).
- Для каждой колонки показать, какие токены выжили, и счётчик выживших.
- **Стартовые значения подобрать так, чтобы расхождение было видно сразу, без возни с ползунками** — используй проверенный пример из Global Constraints: распределение `a=0.40, b=0.30, c=0.20, d=0.06, e=0.04`, `min_p=0.15`, `top_k` off, `top_p=0.92` → vLLM оставляет 3, HF оставляет 4. Токенам дать осмысленные русские имена вместо букв.
- Когда наборы расходятся — подсветить именно тот токен, который выжил в одной колонке и умер в другой, и показать явную плашку вроде «наборы разошлись». Когда совпадают — плашка нейтральная. Это главный сигнал компонента.
- Под компонентом — короткое пояснение механизма **в правильной формулировке**: min_p, отработав первым, убирает хвост; top_p затем считает по перенормированному распределению и добирает порог раньше. **Не писать**, что в HF порог min_p становится строже из-за перенормировки — это неверно, решение min_p инвариантно к перенормировке.

**Проверка (обязательная).** Портировать обе цепочки в скрипт и подтвердить:
1. на стартовых значениях vLLM даёт 3 выживших, HF — 4;
2. существуют настройки, при которых наборы **совпадают** (компонент не должен создавать впечатление, что порядок расходится всегда);
3. min_p в изоляции даёт один и тот же набор независимо от того, применён он до или после перенормировки (та самая инвариантность) — это защищает от соблазна реализовать неверный механизм.
Приложить реальный вывод по всем трём пунктам.

**Сборка и коммит:** `npm run build`, затем коммит только этого файла.

## Task 3: SamplingFunnel (Часть 4)

**Files:** Create `src/components/article/SamplingFunnel.tsx`

**Что должен показывать.** Конвейер целиком, от словаря до одного токена — Часть 4 сейчас без визуала. Это обзорный компонент: он не вводит новую механику, а собирает уже разобранное в одну картину.

Требования к поведению:
- Горизонтальные (или вертикальные) ступени воронки: `словарь` → `после temperature` → `после min_p` → `после top_k` → `после top_p` → `выбран 1 токен`, с числом кандидатов на каждой ступени.
- Ступень `temperature` числа кандидатов не меняет — и это надо показать явно, а не замолчать: температура переформовывает распределение, но никого не убивает. Читатели часто думают иначе.
- Пресеты вместо ползунков: несколько кнопок вроде «код / детерминированно», «сбалансированно», «творческий текст», каждый со своим набором параметров. Пресеты — иллюстративные, так и подписать; параметры каждого показывать рядом.
- Размер словаря брать реалистичный (порядка десятков тысяч) и подписать как иллюстративный.

**Проверка.** Убедиться скриптом, что для каждого пресета числа на ступенях монотонно не возрастают и последняя ступень равна 1. Приложить вывод.

**Сборка и коммит:** `npm run build`, затем коммит только этого файла.
